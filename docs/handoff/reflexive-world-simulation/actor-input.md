## 1. Decisions recommended for the plan

1. Introduce a separately versioned, typed **simulation actor model** derived from admitted research evidence and explicit scenario assumptions. Preserve the existing 17-dimension intelligence contract. The present role/context contracts supply valuable provenance and behavioral evidence, but neither is an executable inventory of rights, resources, obligations, or actions.
2. Add a deterministic **readiness check per actor and action family**. Existing dimension/family coverage is insufficient to establish a particular action's authority, resource requirements, units, counterparties, or prerequisites. Unknown critical inputs remain explicit gaps; they never become unlimited capacity or unrestricted authority.
3. Compile a new **actor-visible decision brief** from permitted beliefs, observations, own state, and a bounded action menu. Keep modeler evidence outside the actor's input bytes. Existing role prompts include research-only findings with warning labels; labels alone do not implement private information.
4. Give v3 research and sealed legacy research explicit adapters into the new model. Do not upgrade unsealed v3 prose to sealed intelligence by renaming fields, inventing receipts, or disabling the existing strict checks.
5. Separate actor proposals from counterparty consent and implemented consequences. A supplier, regulator, coalition partner, or board must have its own bounded decision rights and acceptance conditions. A principal's objective cannot authorize another actor's action.

All names below for new contracts and fields are proposals for the coordinator to freeze in PLANS.md. Existing behavior, gaps, proposed design, and unresolved questions are distinguished explicitly.

## 3. Proposed minimal typed actor contract

Use a new `simulation-actor/v1` artifact with an immutable initial model and references to separately changing world/actor state. Do not mutate sealed research claims when an actor learns or changes its objectives. A later observation or decision event should record that change and its basis. No universal scalar utility function is required.

Every behavioral parameter should carry an evidence/assumption reference, temporal scope, and value status. Collection fields additionally need `collection_status` (`specified`, `known_empty`, `unknown`, `not_applicable`); an empty array alone cannot express all these states.

|---|---|---|

Organizational mandates and represented interests are separate from a display role. | S3, S12, S13, S15. Retain admitted IDs; prohibit fuzzy identity resolution for actions and private recipients. |

## 4. Research, ontology, and compatibility changes to include in the plan

### Research additions

Prefer an additive structured candidate artifact over changing the meaning or required dimensions of `actor-intelligence/v1`. Each candidate needs `actor_id` or a resolvable cast identity, target component/field, typed proposed value, source-claim references or exact report-span reference, temporal scope, and unresolved questions. Evidence extraction can propose a value; deterministic validation decides whether its units, actor ownership, and action meaning are supported.

For sealed legacy input, derive candidates from the original dimensions/qualifiers and their sealed supports (S1–S3), before lossy role/config rendering. Do not extract operational parameters from the 1,800-character config projection or a truncated role prompt (S8/S11). If a new qualifier is needed, adding it only to a prompt is insufficient: the producer's allowlist, claim-identity projection, validators, and consumers must agree. The smaller initial change is a sidecar mapping existing claim IDs to operational fields.

For research engine v3, add an explicit typed-candidate output and validating adapter; current `normalize_actor_rows` drops fields outside its known output and finalization strips intelligence markers (S4). Bind candidate report spans to exact report bytes and preserve source references where available. A report-derived assertion is initially `report_excerpt`, not a legacy fetched-source receipt. Promote it to source-backed support only after actual source-content/quote validation with honest engine-specific provenance. Never synthesize Track-B receipt IDs for v3.

A v3 fallback actor containing only name/type/role cannot satisfy operational readiness. Return an actor/action-family gap report. In a deliberately synthetic scenario, an explicit scenario configuration may supply the missing parameters as assumptions. In an empirical scenario, missing critical authority/resource/counterparty details must block that action family or require documented scenario assumptions before readiness is claimed. Noncritical gaps need not prevent unrelated, fully specified actions.

### Ontology additions

Reuse the existing rich archetypes and relationship direction metadata (S14); do not ask ontology generation to invent executable rules. Add explicit mappings from selected graph entity/edge IDs to typed actor, asset, resource, institution, jurisdiction, and commitment references. Persist the selected domain action/rule catalogue's version alongside this mapping. Conceptually identical types can have different domain mechanisms.

The graph remains an evidence/retrieval projection. A `SUPPLIES` edge does not establish deliverable quantity; `REGULATES` does not enumerate legal powers; `CAUSES` does not supply an equation. Numeric balances, permissions, consent, and predicate implementations must come from validated typed state and approved domain definitions. A named causal edge without a mechanism remains explanatory evidence.

The current ontology/context input may be modeler-facing. Actor-specific retrieval must enforce observation permissions before returning node summaries, relation text, or report excerpts. Merely adding a `visibility` attribute to graph text is not an access-control implementation. Unknown graph classification must not turn a source, rule, or asset into a decision-making actor through the legacy default-eligible path (S13).

## 5. Feasible action menu and private observations

The actor-input boundary should produce three artifacts/concepts:

- **Modeler actor model:** full evidence, uncertainties, candidate parameters, rejected mappings, and source receipts. It can contain unavailable/private facts but is never passed wholesale to the acting model.
- **Actor observation:** `actor_id`, observation ID, local decision-view version, permitted own/public/private facts, observed offers/events, observation time, validity, source/channel identity safe for that actor, and explicit uncertainty. Its audit binding to the full world snapshot remains outside the actor-visible body.
- **Actor decision brief:** permitted persistent objectives/values/beliefs plus the current observation and menu. Only admitted actor-visible fields enter prompts, model tools, histories, summaries, and retries. Audit hashes and paths that reveal hidden global changes stay modeler-side.

Each proposed `ActionTemplate` needs a stable ID/version, semantic verb, actor and target kinds, typed parameters/units, required authority, capability and resource references, known prerequisites, required counterparties/approvers, allowed recipients, and a registered domain-mechanism reference. A proposed `ActionIntent` selects a menu item and parameters, identifies proposer/represented actor and counterparties, and references the visible observations used. It may include a short choice rationale; it cannot submit arbitrary world deltas or declare another actor's consent.

Keep the first catalogues concrete and bounded:

| Synthetic catalogue | Example menu entries | Required distinction |
|---|---|---|
| Investment/supply | `propose_supply_contract`, `counteroffer_supply_contract`, `accept_supply_contract`, `authorize_investment` | Proposal parameters include quantity, unit, price basis, delivery window, and named party; authorization references an investment and mandate. Agreement, resource reservation, and productive completion are separate effects. |
| Policy/trade | `propose_rule`, `authorize_rule`, `apply_for_license`, `issue_license` | Proposal/authorization scope references a named jurisdiction and rule; the applicant cannot issue its own license. No universal tariff-to-demand equation is implied. |
| Coalition/institution | `offer_coalition_terms`, `accept_terms`, `cast_vote`, `exercise_veto` | Terms identify parties and obligations; vote/veto require mandate and motion references. Positive relationship valence cannot supply another member's acceptance. |

A deliberate `wait` is a valid choice when its domain costs and outstanding commitments are accounted for. Information requests and withdrawal are available only where a registered channel or reversible commitment permits them. A missing executable action should yield a reasoned readiness gap or constrained choice, not a fabricated capability. Menu schema describes admissible choices; it does not force the actor to take a predicted “likely action.”

The common validator should check schema, reference identity, known own resource/authority limits, and the registered template's preconditions. Domain-specific implementations define permitted transfers, investment completion, licensing, voting, sanctions, or negotiation. Use bounded named predicates and parameter schemas rather than executable code or arbitrary equations generated by the model. This contribution specifies input obligations, not round sequencing or transaction resolution.

**Information-safe feasibility:** A visible menu cannot be filtered using inaccessible counterparty facts in a way that reveals them. If supplier B's remaining capacity is private, A can submit a valid request based on A's own known budget; the request is contingent on B's acceptance and feasibility. It must not disappear from A's menu merely because the simulator knows B is full. Secret capacity, private vetoes, or unknown willingness are not reported as actor-visible rejection reasons. The action catalogue distinguishes “can request/propose” from “can unilaterally execute.” An unknown own authorization blocks unilateral execution; a registered request-for-authorization action may remain available.

**Observation admission:** Preserve literal-boolean access semantics and explicit denial precedence from S6. Extend access to explicit actor-ID recipient sets and channel scopes. Public source availability does not by itself prove observation, comprehension, sincerity, or common knowledge. An explicitly configured public broadcast can deliver a public fact to specified observers; private offers go only to named participants. A rumor can be observed without becoming a verified world fact. New evidence may revise actor beliefs while leaving other actors' beliefs unchanged. Belief revisions need observation references; unsupported assertions remain hypotheses and cannot create rights or resources.

**Own preferences versus external knowledge:** A documented actor-specific motivation may justify initializing a behavioral preference; an analyst hypothesis about that motivation must stay labeled as a scenario assumption if used. It cannot quietly become the actor's self-knowledge. Likewise, a documented internal control or resource can be represented in the world without automatically exposing all its details to every organizational representative; the mandate/access mapping decides what that representative sees.

Do not reuse the existing role prompt verbatim as the new decision brief: S9 shows modeler calibration findings already present in actor-facing text.
