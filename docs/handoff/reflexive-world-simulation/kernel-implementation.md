## Concrete integration details

- Store initialization calls `initialize_world(spec) -> snapshot`. Initial event receipts are retained in `snapshot.initialEvents`, and their stable IDs enter `appliedEvents` before observation.
- `validate_mechanisms(spec)` expects a structurally normalized specification from `validate_spec`. Reducer entry points invoke both checks themselves.
- Rate metrics strictly use `<account unit>_per_day`; `kind` must be `rate`. For the shared example, `goods_per_day` is compatible with the `goods` transfer accounts; generic `units_per_day` and plain stock-unit `goods` are not. Fixed `ratePerDay` is denominated in the source account's units per day.
- Prepared priority rules currently have `{ruleId, priorityId, value, trigger: {section, recordId, value}, basis}`. The trigger section is metrics/rules/relations; the record must be visible and equal the fixed trigger value at observation time. Updates have `{ruleId, priorityId, value}` and receive immutable observation/decision provenance. This concrete shape needs coordinator acknowledgment in shared contracts.
- Template visibility defaults conservatively to analyst-only. Offer envelopes always disclose exact terms to their parties unless explicitly public. The coordinator should declare explicit template visibility for desired public action events.
- Messages retain `kind: message` and `status: accepted` as nonbinding envelopes. The coordinator has now added a separate delivered-message projection to observations; this worker confirmed the `messages` field in the current consumer. The coordinator also reports explicit public visibility for example templates and assumptions.
- Atomic bundles may contain physical actions, or communication with optional waits, but not both communication and physical actions. Mixed bundles reject before staging or mutation, so a rejected bundled withdrawal cannot suppress an eligible recipient's response slot.
- Flows must have unique source accounts, and no flow target may be another flow's source. Competing or coupled processes require a separately declared allocation/process mechanism. Admission rejects them rather than inventing boundary-dependent allocation; independent flows remain invariant to unrelated time splits.
- Readiness requires a nonempty policy `authorityIds` list and specified, non-None initial values for `requiresRule`/`mandateRule` dependencies and numeric metrics consumed by investment, scheduled deltas or flows. Known false prerequisites/mandates remain ready; their current state can reject an action until a later policy enables it. Unknown unrelated metrics and rule-set targets remain admissible. `validate_mechanisms` raises `invalid_mechanism`; the shared compiler translates mechanism failures to preparation `modeling_gap`.
- At initialization and round close, `lastActionResults` retains only the actor's own latest nonempty resolution batch, capped at `maxIntentsPerPhase * 2`. The actor's `lastObservedEvents` retains a rolling window of records passing `visible_to(event, actorId)`, capped at `maxInboxItems`; `observedEvents` contains exactly their IDs. Filtering happens before deduplication/truncation. Quiet rounds preserve the last available feedback for slower decision cadence; all receipts retain their original round/timestamp, and actor-proposed state updates cannot overwrite these keys.
- Interaction receipt feedback also respects `deliverAt` for recipients. The reducer-owned top-level `pendingFeedbackEvents` queue retains deferred receipts through committed quiet rounds; it is absent from actor observations and is carried by the existing whole-snapshot Store closure. Senders receive their own permitted receipts immediately without re-insertion on each later quiet round.
- Raw `flow_transfer` integration receipts remain in the ledger. Actors receive canonical `flow_summary` events instead: one real emitted event per flow/period, with the actual total, declared visibility/basis, period endpoints and an ID independent of internal split points. Summaries also enter `appliedEvents`. This prevents unrelated private boundaries from leaking through feedback timestamps/counts or evicting visible memory.
