# Proposed next feature: one durable run-spending boundary

**Status:** Approved for offline implementation by the user on2026-10-29. This authorizes code work only; no provider spend, scheduler activation or deployment. The approved sequence starts after delivery of the completed acceptance slice.

## 9. Implementation plan for approval: one durable spending boundary

### 9.1 Decision, scope and measurable endpoint

Implement **one private authorization manifest, one run-bound SQLite database, and pre-dispatch adapters at the actual model/tool calls**. Keep the existing pipeline, typed case, model gateway, actor rules, report path and count limits. The first release supports only this new target-first operational run in a source-isolated runtime. It is not an account-wide billing service or a migration of existing saved runs.

The conservative first-release rule is **no reservation refunds or allowance recycling**. Each physical attempt permanently consumes its quoted maximum from this run's authorization, whether its response succeeds, fails, is empty, is cached by the remote provider, or remains unknown. Response usage is recorded separately. Local cache hits that never dispatch consume no new reservation. This is deliberately stricter than the world evaluator's known-usage release rule. It avoids an invoice-reconciliation feature, uncertain refunds, and treating estimated usage as money returned to the allowance. It may stop a useful run earlier than necessary; stopping early is acceptable for this acceptance exercise.

The acceptance invariant is:

`sum(all_committed_attempt_max_usd) <= immutable_authorized_cap_usd`

After an admitted route's finite maximum charge is established, its physical attempts are bounded by those retained maxima. Store fixed-point **integer micro-USD**, rounding each reservation upward; parse the manifest's cap as a decimal string exactly representable in that unit, with no binary-float arithmetic or cap rounding upward. Validate finite/nonnegative rates and SQLite integer limits. For example, a future approved USD 5 cap would be 5,000,000 micro-USD; the suggested figure in section 5 is still not authorization.

Success means fake parent, research child and tool transports compete for the same immutable balance; no network invocation is possible without a committed reservation; a clean resume keeps every prior reservation; and failure, missing storage or missing context never switches the bound run to an unmetered path. No proof of that behavior is claimed until the planned guarded acceptance passes.

This is a cap on application-authorized external variable expenditure, conditional on verified tariff/request bounds and the supported transport actually honoring its wire limits. It is not proof of an invoice or protection against an unbounded/incorrect provider tariff. If those assumptions cannot be established, deny the route or require an independently verified hard provider-side spending limit. Do not rename a cost estimate a hard maximum to make admission pass.

### 9.3 Spending classes and evidence vocabulary

The manifest classifies each allowed route **before client construction**. Unknown classification blocks admission.

| Class | Budget treatment | Receipt language |
|---|---|---|
| Per-use external model API | Reserve a verified conservative USD maximum for complete input, output including reasoning, any cache-write premium, fixed fees and applicable bounded surcharges. | `reserved_max_usd`; optionally `provider_reported_usage` and `priced_usage_estimate_usd`. Only an independently reconciled bill/charge receipt may populate `verified_billed_usd`. |
| External paid tool/credits | Reserve the maximum credits/units permitted by the exact payload times the verified conservative USD unit valuation, including add-on fees. Prepaid credit consumption remains visible external resource consumption. | Separate `reserved_tool_units`, `reported_tool_units`, and their valuation basis. A cached Firecrawl response or HTTP error is not assumed free. |
| Verified zero-marginal-charge public transport | A zero USD quote is allowed only for an explicitly admitted route with supporting evidence; still count and record the request, endpoint and rate/time bounds. | `external_charge_class=verified_zero`; never infer it merely because no key is needed. No such extra route is required by the initial profile. |
| Subscription-backed CLI/proxy/coding plan | Subscription request/token/quota usage and fixed subscription fees are a different accounting scope. Do not derive USD charges from the public API price table or claim zero resource cost. | `subscription_usage`, separate from external USD totals; fixed subscription cost is not billed to this pipeline. **The first capped profile does not support dispatch through these routes**; adding an adapter/quota policy is outside this feature. |
| Unverified API/proxy/subscription status | No quote can be admitted. | `billing_class_unverified`, with credential presence only. |

Thus the observed `glm-5.3` selectors and credential presence do not establish whether that particular route belongs to the per-use or subscription class. The future run remains blocked if its configured route cannot qualify. Do not silently replace the user's route, create an account/key, or treat the proposed cap as a purchase authorization. External invoice lookup and subscription-quota monitoring are not part of this implementation.

For the smallest supported live profile, allow one qualified OpenAI-compatible model route in both parent and child, plus one explicitly priced Firecrawl search/scrape route. Disable all model fallbacks, tier/provider switching, Serper/Tavily/DDG delegate selection, Jina/Exa/direct-fetch fallback, MCP/data/news/market/social enrichment and extract-only salvage. The parent free probe is separate and unchanged. Other enabled credentials must not select an unpriced route; scrub them from the private runtime and enforce the route allowlist in code as well.

Quotation happens after final request parameters, reasoning headroom and JSON/tool schema are fixed. Do not use `estimate_tokens()`, character heuristics, or the gateway's weighted units as a proven token ceiling. Require a checked input upper bound that includes framing and tool schemas, backed by the admitted tokenizer/protocol; otherwise reserve the provider's verified enforceable full input/context ceiling or refuse. Reserve the actual wire output maximum, including widened retries and hidden reasoning. If this conservative quote cannot fit the proposed cap, stop before dispatch rather than increasing the cap or understating the quote. Existing provider usage estimates remain useful diagnostics but cannot reduce reservations in v1.

### 9.4 Authority, schema and identities

The local manifest, proposed schema `target-run-spending/v1`, lives at `R/spend/authorization.json`. It contains an opaque `authorization_id`, canonical question/request hash, target mode/path/period/seed settings, cap decimal/currency, source/import manifest hash, tariff/route hashes, allowed physical request bounds, billing classes, and explicit resume policy. It contains no credentials or raw prompts. A private sibling request file retains the reviewable JSON from section 5. The source/runtime receipt binds `R` and the supported spending version. This manifest is a record of a **future approval**, not something the code can self-authorize.

The dedicated database is `R/spend/run.sqlite3`, outside pipeline uploads, handoff copies, research budget epochs and forks. Proposed minimal tables:

| Table | Required facts/invariant |
|---|---|
| `run_authorization` (one row) | Schema version, authorization ID, manifest/route/tariff/source hashes, root identity, immutable cap, once-bound pipeline ID, current generation and dispatch state. Cap, identity and binding are not mutable through API/resume. |
| `attempts` | Authorization ID, unique `attempt_id`, logical operation key, monotonically allocated ordinal, owner generation/participant, stage/call seam, route and billing class, canonical request hash, maximum input/output/tool units, integer maximum charge, state, timestamps, optional provider request ID hash and receipt hash. Unique `(authorization_id, logical_key, ordinal)`. No request/response body. |
| `events` | Append-only bounded lifecycle/denial/observation records, including charge-basis tags, outcome/usage hashes, fence changes and stop reason. Repeated identical outcome is idempotent; conflicting outcome is an integrity error. No free-form provider exception text. |

The balance is derived from immutable attempts, with an optional transactionally maintained cache cross-checked against their sum. Receipts may change an attempt's outcome but cannot delete it or change its reserved maximum. Keep schema and currency fixed; reject unknown versions.

Identity rules:

- **Authorization/run identity:** one authorization ID is bound once to one pipeline ID. A changed task ID, process PID, resume count, `RESEARCH_BUDGET_EPOCH`, model instance or copied handoff never creates a new allowance. Binding must commit before thread/child launch. If a crash occurs between database binding and pipeline-state persistence, recover that same ID from the binding or refuse; never mint another pipeline to consume the same authorization.
- **Logical operation identity:** use stable producer context plus a canonical input hash. Research uses target checkpoint generation, phase, KIQ/tool-step or JSON-call label and input hash; estimator uses case/policy/context hash plus method name; actor uses case/seed/path/period/opaque actor and observation hash; a tool uses its owning research operation, normalized query/URL hash and exact payload hash. A persisted ordinal distinguishes intentional repeated operations. Request hashes alone are not a billing deduplication key.
- **Context transport:** operation metadata travels out of band in the explicit gateway context/contextvars, copied into worker threads and sent as the required child contract. The simulation caller supplies path/period identity; do not append billing/run metadata, hidden actor state or raw identity to the actor-visible observation to obtain a ledger key. Identical validated local cache results can reference an earlier physical-attempt receipt without new dispatch.
- **Physical attempt identity:** every actual model invocation, JSON repair, reasoning refusal resend, known transient retry and tool POST gets a new attempt ID/ordinal and its own reservation. The SDK/provider request ID is a receipt attribute, not the primary identity. Never assume a provider honors an idempotency key unless that route's contract proves it.
- **Local at-most-once claim:** an already claimed attempt cannot be dispatched a second time, even with identical payload bytes or after restart. A repeated reserve/claim for that attempt either returns its stored receipt without dispatch or refuses. If a completed logical operation has lost its reusable result, repeating it is a new physical attempt using the same remaining run allowance, never reuse of its old permission.
- **Private metadata:** operation/request hashes and aggregate dimensions are sufficient for published diagnostics. Keep provider request IDs, payloads and any actor context private under `R`; ledger error/status strings are allowlisted codes, not exception messages.

There is no new HTTP `budget_usd` parameter. The private runtime is booted with one reviewed manifest; the existing `PipelineOrchestrator.start` validates the normalized request against it. Both `/api/research/run` and `/api/v1/run` already reach that method. This keeps ordinary public request contracts unchanged while making direct-start calls and both HTTP routes obey the same single-run authority in this private mode.

### 9.5 Transactions and lifecycle semantics

The strict module exposes only narrow operations such as `create_authorization`, `bind_pipeline`, `open_existing`, `reserve_and_claim`, `record_observation`, `halt`, `resume_existing`, and `summary`. Only the private launcher can create an authorization, and only before a pipeline has been bound. Provider adapters may open existing state and reserve/record; they cannot initialize a missing DB, raise a cap, change pricing, reset a counter, or unhalt a run.

`reserve_and_claim` validates manifest, required context, root, generation, dispatch state, actual route/payload bounds and remaining capacity in **one `BEGIN IMMEDIATE` transaction**, inserts an `unknown` attempt and its immutable maximum, and durably commits before invoking the transport. `synchronous=FULL` and atomic creation follow the existing world-store pattern. Lock/database errors deny dispatch. Do not hold a transaction during network I/O. The commit is the admission linearization point: a call admitted just before cancellation may still reach the network, but it is already fully reserved; cancellation cannot promise to recall it.

| Event | Required behavior |
|---|---|
| Successful/empty/invalid response | Capture available raw usage metadata at the transport boundary before parsing/validation can throw. Record `response_observed` and preserve the full maximum. A response without usage remains unknown **usage**, not zero cost. No allowance refund. |
| JSON repair or known, price-bounded retry | Same logical operation, new physical attempt and quote. Recheck cancellation/fence/balance at the raw dispatch. Missing allowance stops the whole run. The initial profile disables route fallback; unsupported fallback is rejected even if configured later. |
| Timeout, connection reset after possible send, ambiguous 429/5xx or killed process | Keep the entire attempt maximum, record unknown outcome and latch `halted_unknown`. No automatic retry/fallback or new dispatch in the one-run profile. Provider status alone does not establish zero bill. A late response can add evidence but cannot restore allowance or automatically reopen dispatch. |
| Crash before reservation commit | No transport call is permitted. The transaction rolls back. The already-bound authorization remains the same on clean restart. |
| Crash after commit but before/during/after send without durable result | Keep the reservation as unknown. There is no safe inference that it was unsent; do not replay that attempt. Recovery must not reset the database or cap. |
| Cancel | Commit `halted_cancelled` before setting the existing cancellation event/killing the owned child. Child dispatch checks the same DB, not just an in-process event. Already admitted attempts remain reserved. Cancellation is terminal for live dispatch under this first-release authorization; evidence inspection/local rendering may continue. |
| Denied quote, invalid route, missing context, corrupt/missing ledger, price/source drift | Fail closed with a typed spending-stop code and no transport call. Persist the stop when storage permits; if not, process-local denial plus strict existing-file access still forbids further dispatch. Do not convert it to an empty source, unavailable estimator, held actor action, provider fallback or success. |
| Clean resume after a recoverable non-spending failure | Requires explicit later user resume authorization, matching source/config/request, same pipeline and DB, no unresolved in-flight/unknown outcome, and exclusive ownership of the old process tree. Increment the writer generation, not the cap; old participants cannot reserve. All prior maxima remain debited. |
| Exhaustion/unknown/cancellation/completed run | Resume cannot reopen dispatch or renew allowance. Local read/reconciliation is allowed. A new authorization/run is a separate proposal, not a resume trick. No forced-resume bypass. |
| Fork/continue/duplicate start | Reject forks of the bound run and repeated new starts before any dispatch. This profile starts in `full` mode, so research-only→full continuation is not needed; reject that scope change. Duplicate HTTP start returns the existing binding or a conflict, never another task/cap. |
| Meter reset or telemetry disabled | No effect on reservations. `LLMMeter` and `[usage]` aggregation remain observational; synthetic parent research rows never charge the spending ledger a second time. |

Writer recovery should reuse the world-store launch-lock/fence discipline. The private parent holds an exclusive run lock; child participants belong to that generation and are identified with durable spawn receipts. Parent lock availability alone does not prove a surviving child or timed-out worker has exited. Require verified owned-child exit before generation takeover; if uncertain, remain halted. No reservation expires on a PID timeout, lease TTL, clock change or child death. This is a trusted local-process boundary, not protection against an administrator intentionally restoring an older ledger or running a different binary; copying/restoring/rewinding the active ledger is explicitly unsupported and ends live eligibility.

### 9.7 Source-isolated runtime and durable artifacts

This plan tightens LR-3 through LR-7. For the smallest feature, the proposed **headless launcher replaces the earlier loopback Flask server suggestion**; both HTTP admission routes are exercised offline through their existing test clients. The actual future operational run invokes the same common start method once and needs no listening service. It does not call `create_app()`, `backend/run.py`, production orphan reconciliation, or a scheduler.

- Use `R/app` and `R/deer-flow` with regular private source files and a hash-bound dependency/import map. Start the launcher with isolated/no-site/no-bytecode Python; do not execute deployment `.pth` files. The same no-site import isolation must be established for the child, not merely for the parent. A private validated venv is acceptable, but its package origins must not resolve back to deployment source. Do not repurpose `HOME`, `home`, `CODEX_HOME`, or `USERPROFILE`.
- Before any application import, validate canonical root, path ownership, no writable symlink escapes, exact nonsecret control manifest, required billing classes, private dependency origins and disabled extra routes. Only a later explicit live action may load the necessary existing credentials privately; values never enter argv, manifest, summaries or errors. No source or credential provisioning is performed by this planning task.
- `R/spend` is distinct from `R/app/backend/uploads`. Required-spending state survives ordinary pipeline deletion/cleanup and research epoch creation. `DEERFLOW_DIR`, child home, model lease DB, logs, temp files, search/fetch caches and optional cache roots all resolve inside `R`; include SQLite WAL/SHM files and private child working directories in the path audit. Credential presence is a boolean, never a receipt of account validity.
- Preparation must explicitly prevent root `.env`/ancestor dotenv from overriding the pinned controls. Install a minimal reviewed nonsecret private configuration plus only the allowed credential injection, and assert effective route/control values after config load but before client construction. On resume, changed model, fallback, billing class, tariff or source hash is a refusal, not a new quote policy.
- Keep scheduler/extra provider controls disabled exactly as in section 5, and additionally enforce the narrowed search/fetch allowlist described above. Allowed env settings are corroborating controls; dispatch guards enforce the manifest if env changes.
- Reserve the authorization once in a durable private archive registry outside ephemeral runtime cleanup; it records the one root/pipeline binding and cannot be reused to initialize a replacement `R`. The active SQLite DB remains at its bound location during the run. Archive through SQLite's consistent backup/checkpoint procedure after owned processes exit, preserving manifest, DB, WAL-consistent state, aggregate receipts and hashes. An archived copy is read-only evidence, not a fresh live authorization.
- The required-mode launcher fails if the root was cleaned, ledger is missing, authorization was consumed, old code lacks this schema, or a moved/restored snapshot is presented as active state. Do not reconstruct spending from `run_telemetry.json`, reinitialize an empty DB, or delete receipts to “recover.” Preserve uncertain artifacts and return to review.

The durable archive registry is a single private authorization/binding record for this run, not a new scheduling service. It exists so cleanup or recreating an ephemeral directory cannot turn the same approval into a new cap. Initial creation/binding order must be crash-safe: consumed/bound registry first, ledger and matching pipeline next, then dispatch; incomplete preparation may be repaired only with the same recorded identity and no prior dispatch, otherwise it remains stopped.
